## What was implemented (packages/llama/src/llama/desc_list.py)
- `Cleaner` type alias, as the brief specifies.
- `drop_leading_artist_items(parsed, artist)` drops only the LEADING run of items whose `jerrybase.artist_key` equals the artist's. An empty key is a no-op.
- `_parsed_lines(desc)` mirrors `parse_setlist`'s preprocessing and its header truncation (first marker, `_may_start_a_show`, the `_RECOVER_FLOOR` probe through `_emit_items`). The lines it returns are exactly the ones `parse_setlist` parses, so the lines truncation removes are exempt by construction.
- `read_parse(desc, *, artist, clean) -> DescList | str` works in this order:
  1. Any line matching `_EMPTY_NUMBERED` returns `"empty entry"`. This is the same line-level check reader (i) makes, so "a numbered line with no text makes both readers inadmissible" holds.
  2. `parse_setlist(desc)`. Each non-empty parsed raw line gets a per-line count from `_emit_items([line])`, judged on the raw line alone, so the document-level `_NUM_PREFIX` strip does not apply. If the counts do not sum to `len(parsed.items)`, it returns `"per-line count disagrees"`. An empty parse returns `"no items"`.
  3. It calls `clean(parsed)`. If the cleaner's output length matches its report, it then applies `drop_leading_artist_items` to the cleaned parse and maps those indices back into `removed`.
  4. Exempt lines are:
     - the line of any item in `removed`;
     - a 0-item marker line (`_SET_LINE`, `_LABELED_SET_LINE` or `_ENCORE_LINE`);
     - a 0-item `_NOISE` line.
     Any other line whose count is not 1 returns `"line yields {c} items: {line}"`.
  5. A cleaner whose report disagrees with its output returns `"cleaner count disagrees"`. An empty cleaned list returns `"no items"`.
  6. The output is `DescList("parse", raws=cleaned item titles, clean_entries(raws), blocks, boundaries)`. Blocks are runs of equal `SetlistItem.set`. The boundary is `"encore"` when the new block is encore, otherwise `"set"`.
- `DescRead(used, numbered, parsed)` and `read_desc_list(desc, n_tracks, *, artist, clean)`. `used` is the first of (i) or (ii) that is a `DescList` with exactly `n_tracks` raws.
- New imports: `jerrybase`, `models.ParsedSetlist`, and setlist's `_ENCORE_LINE`, `_LABELED_SET_LINE`, `_NOISE`, `_RECOVER_FLOOR`, `_SET_LINE`, `_emit_items`, `_may_start_a_show`, `parse_setlist`. These are all on the brief's allowed list. No stage module is imported.

## Judgement calls (please confirm)
1. **`artist` on `read_parse`.** The `Cleaner` is pre-bound, so the brief's `artist` parameter would otherwise go unused. `read_parse` therefore applies `drop_leading_artist_items` itself, AFTER `clean`. With `gather_cleaner` (Task 11), which runs the same drop after the banner strip, the second drop is an idempotent no-op. Running it after the cleaner means gather's banner-strip input matches `build_canonical`'s exactly. With an identity cleaner, as in Task 7's test, a leading artist line is still dropped.
2. **Exemption of partly removed lines.** I followed the plan text literally: "the lines of the items in removed_indices are exempt". A line is exempt if ANY of its items was removed. The brief's test (a banner line yielding two items, the cleaner removes item 0 and reports `{0}`, result admissible) requires this. Consequence, pinned in the test: the surviving sibling item (`Boulder CO`) stays in the list as an entry, because the cleaner decides the list. The stricter alternative would require ALL of a line's items to be removed; it would fail the brief's test as written.
3. **A cleaner whose report disagrees with its output** returns `"cleaner count disagrees"` and does not raise. The brief's "same cleaner reporting frozenset()" must return `"line yields 2 items: …"`, so the line judgement runs first and the contract check comes after it.
4. **Raws.** For reader (ii), `raws` are the cleaned items' titles (after `parse_setlist`'s own prefix strip and the cleaner's rewrites), not the raw line text. `cleaned` is `clean_entries(raws)`.
5. **Header-only** means a line that matches a marker regex and yields 0 items on its own. A header with inline songs counts as an ordinary line: one song is fine, two make the list inadmissible.
6. **Lines yielding 0 items.** Per the spec's literal rule ("every other non-empty line must yield exactly one item"), a non-exempt line yielding 0 items makes (ii) inadmissible. Examples are an over-80-character prose line and a `Total Time …` line in the body, both of which `parse_setlist` drops as junk. This may cost yield on lists with a total-time footer. Lineage lines are exempt through `_NOISE`.
7. **`used`** is the first count-matched admissible list in the order (i), (ii). If (i) is admissible but not count-matched and (ii) is count-matched, (ii) is used; this is pinned by `test_count_matched_parse_used_when_numbered_is_not_count_matched`. "Both qualify" is read as both being count-matched and admissible.
8. **`read_desc_list` calls `read_numbered(desc)` with the default `encore_header=False`**, as the brief's signature implies.

## Concerns
- Call 2 lets a partly stripped banner line put its unstripped fragment into the list. With `gather_cleaner` this needs a banner line split by `,`/`;` whose items the banner strip only partly removes, which is rare. D's later checks (count match, hygiene) should catch it. The orchestrator may prefer the all-removed rule; the change is one line in `read_parse`, and the brief's test would change with it.
- Exact per-line attribution relies on the sum check. If the counts sum correctly but are mis-attributed (one line +1, another -1 in document context), nothing detects it. The only context-dependent count change is the enumerated `_NUM_PREFIX` strip, and that can only remove items, so a compensating +1 cannot arise.
