the `except RateLimited` handler re-raises and there is no pacing on limit

CLAUDE.md, phase 1 recognises no openrouter response as a window exhaustion).

true and useful — is served correctly.

rendered shape, and choosing between the candidate fixes is a design call.

- (b) In `_execute`, print only when `reading is not None`. One line, but
  loses the "the proactive gate is blind this run" warning entirely.
- (c) Leave as is and reword the string to something true in all three cases
  (e.g. `"usage meter not read — no proactive pacing this run"`). One line, but
  `llama pacing` then answers a direct question with a vaguer sentence.

fix alongside Concern 1 if you take (c).

## G1 — the forecast now follows the binding window

**Changed** (`packages/llama/src/llama/pacing.py`):

- **`shows_that_fit` now takes ONE METER, not a whole reading.** This is a
  deliberate change to a surface the brief pinned; the reason is below.
- Added `Forecast(shows, scope, resets_at)` (frozen dataclass) and
  `binding_forecast(reading, per_show_delta, opts) -> Forecast | None`.
  It calls `shows_that_fit` once per window, **each against its own ceiling**
  (`five_hour_ceiling` / `seven_day_ceiling` — independent config fields that
  merely share a default of 90), takes the smaller count, and carries **the
  binding window's own** `resets_at`.
- **Ties go to the weekly window.** `min` keeps the earliest minimum and the
  weekly candidate is listed first, because on a tie `decide` pauses on

### The three things you asked me to handle explicitly

**1. Separate ceilings.** Each window is measured against its own field. Pinned
by `test_each_window_is_measured_against_its_own_ceiling`, which lowers only
`seven_day_ceiling` to 50 and asserts the weekly binds *even though its meter
reads lower* (40) than the session one (60) — a case a shared ceiling cannot
express, so the test cannot pass by accident.

**2. The time format.** I picked: **the 5-hour reset stays a bare `%H:%M`; the
weekly one names its window and carries its date** —
`the weekly reset, Sep 8 16:00`. Reasons: a 5-hour reset is by construction
within five hours, so a bare clock time is unambiguous, and adding a date
there would be noise on the common case (it also keeps every existing
assertion's rendered form unchanged). A weekly instant days out as bare
`07:00` reads as "this morning", which is worse than the wrong count because
it looks like a bug rather than a weekly ceiling; and an *unlabelled*
`Sep 8 16:00` would still leave the operator wondering why a session reset is
three days away, which is why the window is named as well as dated. Day
rendered as `{when.day}` rather than `%-d` (not portable) or `%e` (pads, so
`Sep  8` reads as a typo in running prose). The shortfall clause names the
window too — after "~1 fit before the weekly reset", a bare "the reset" in the
same sentence would point at the sooner window the run is not waiting for.
One acknowledged edge: a 5-hour reset that crosses midnight renders as e.g.
`02:00` with no date. That reads correctly as "tonight" and I judged a date
there to be worse; flagging it rather than leaving it implicit.

**3. The `resets_at` guard follows the binding window.** `_pacing_line` now
guards `fc.resets_at`, not `reading.five_hour.resets_at`.
`test_the_line_survives_a_meter_that_named_no_reset` still means what its name
says — I checked its data: `five_hour=Meter(65, None)` with
`seven_day=Meter(7, RESET_7D)` and 4.0%/show gives 6 vs 20, so the **five-hour
window still binds** there and it is still a test about the binding meter
naming no reset. And **yes, the weekly case needed its own test**: two, in
fact. `test_the_binding_windows_missing_reset_is_carried_not_swapped` (unit)
asserts the forecast carries the weekly `None` rather than falling back to the
other window's instant — which would name a reset belonging to a window that
is not what stops the run — and
`test_the_missing_reset_guard_follows_the_binding_window` (rendering) asserts
the line comes out clean with no `fit before` clause and, emphatically, not
the 5-hour instant. Both use `Meter(84, None)`, the shape you confirmed
`Current week (Fable): 0% used` produces today. Mutant N4 (dropping the guard)
reddens exactly those two.

### On the signature change — saying so explicitly, as instructed

`shows_that_fit(reading, per_show_delta, ceiling)` became
`shows_that_fit(meter, per_show_delta, ceiling)`. **Reason:** the old shape had
`reading.five_hour` *in its body*, which made "forecast the wrong window" the
easiest thing a caller could write — and it got written, which is why this
round exists. Adding a second function beside it would have left that trap
loaded: a future caller reaching for the obvious name would silently get the
five-hour-only answer again. Per-window is the only shape that cannot express
the bug, and `binding_forecast` is then a three-line composition.

The three brief-supplied tests were updated **deliberately**, as a named edit
rather than a side effect: each now passes `_reading(...).five_hour` instead of
`_reading(...)` — same values, same intent, one word longer — and a comment
above the group records why the primitive is per-window. My round-1 test
`test_shows_that_fit_treats_a_zero_estimate_as_no_estimate` got the same
treatment; **it and `test_shows_that_fit_is_unknown_without_an_estimate` would
otherwise have passed accidentally** (a `UsageReading` is not `None`, so the
`not per_show_delta` arm still short-circuited), which is exactly the kind of
green I was told not to believe. `shows_that_fit(None, 4.2, 90) is None`
remains valid and now means "no meter" rather than "no reading".

`shows_that_fit` stays public and directly tested; `binding_forecast` is its
