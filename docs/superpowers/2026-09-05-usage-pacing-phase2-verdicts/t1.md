## I1 — dated branch's crash guards were unpinned

Added `test_dated_reset_degrades_to_none_on_a_bad_zone_or_impossible_date`
(verbatim from the review) pinning that a bad zone (`Mars/Olympus`) and an
impossible date (`Feb 29` in 2026, a non-leap year; `Sep 31`, a day that
doesn't exist in any month) both degrade to `None` rather than raising.
Both guards (`try/except` around `ZoneInfo(...)`, `except ValueError:
continue` in the year-search loop) already existed in the Task 1
implementation; only the pin was missing. No source change needed for I1.

## I2 — false ordering-safety comment, undocumented single-clause contract

Three changes, all in `packages/herder/src/herder/limits.py`:

(a) Replaced the two-line comment above `_RESET_DATED_RE` ("Tried FIRST
because it is the more specific of the two; the time-only pattern cannot
match it anyway, since 'Sep' is not a digit") with the real reason:
ordering decides which clause wins when a text carries more than one
`resets ...` clause, since `_RESET_DATED_RE.search` scans the whole string
and matches a dated clause anywhere in it regardless of an earlier
time-only clause.

(b) Added a "Contract" paragraph to `parse_reset`'s docstring: `text` must
contain at most one `resets ...` clause; with more than one, the dated
form wins wherever it appears, silently discarding a time-only clause —
multi-clause callers (e.g. a full /usage listing) must slice per-clause
before calling.

(c) Added `test_dated_form_wins_when_a_text_carries_two_reset_clauses`,
pinning the measured behavior on a two-line blob with a time-only session
clause and a dated weekly clause: `parse_reset` returns the weekly instant.

No behavior change — both fixes are test/doc additions plus a comment
correction.
