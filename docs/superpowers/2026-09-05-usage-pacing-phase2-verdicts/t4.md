## The design point: is the weekly-before-session ordering real?

**Yes, and a reader can see it — with one latent fragility worth naming.**

`decide` ends in `_pause(seven_day, …) or _pause(five_hour, …) or Proceed()`.
`or` evaluates left to right and short-circuits, `_pause` returns either `None`
(falsy) or a `PauseUntil`, and `PauseUntil` is a plain frozen dataclass with no
`__bool__` or `__len__`, so every instance is truthy. The weekly verdict
therefore wins whenever it exists. The docstring states the priority order and
the reason (a weekly exhaustion cannot be slept off at the 5-hour reset), and
the argument order in the chain matches the docstring's numbering, so the code
and the stated rule are readable against each other.

It is carried by dataclass truthiness rather than an explicit `if`, which is
idiomatic but means the property would silently invert if `PauseUntil` ever
gained a falsy `__bool__`/`__len__` — e.g. by being re-cut as something with
container semantics. I judged that too narrow to restructure for, especially
against a brief whose code is meant to land verbatim, and the ordering is now
pinned by execution: mutation **M2** (swap the two `_pause` calls) is caught by
`test_weekly_ceiling_outranks_the_session_gate`. Flagging it rather than
changing it.

Related, and correct rather than a defect: `_pause`'s estimate suffix uses
`if projected` (truthiness), so a projected cost of exactly `0.0` omits
", est …%/show". That is consistent with `progress.per_show_delta or 0.0`,
which already treats `0.0` and `None` alike as "nothing learned yet".
