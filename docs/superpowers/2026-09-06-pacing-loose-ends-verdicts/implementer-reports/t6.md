## Assertions that are MINE, not the brief's

Brief's test, `test_the_preflight_gate_runs_before_interpret_is_paid_for` — I kept it

    ws = RunWorkspace(tmp_path, "gated")
    assert ws.request.exists()
    assert not ws.criteria.exists()

Why. I built the wrong implementations and checked the brief's three assertions against
them. They survive a gate in the wrong PLACE? No — `calls == 0` kills that. They survive
an unrelated early failure? No — `exit_code == 0` plus `state == STATE_PAUSED` kills that
(an unrelated failure exits 1 and never marks the session paused). So the brief's test is
sound on both hazards my dispatch named. The gap I did find is different: all three pass
against a gate that pauses a run NOTHING CAN RESUME — pause before the request write, or
after a partial criteria write, and the test is still green while the checkpoint is
useless. That is precisely the failure Tasks 4 and 5 exist to prevent and the stated
reason this task lands after them, so the pair (request present, criteria absent) is what
`run resume`'s re-interpret branch keys off and is worth pinning here.

My own test `test_resuming_a_criteria_less_session_gates_before_re_interpreting` is
entirely mine. Its docstring says outright that `calls == 0` is the load-bearing line and
that the paused state is NOT — mutation 2 confirms it.

## Deliberate deviation from the brief's prescribed code — please review

The brief's signature is `_preflight_gate(..., *, note: str)` with the identical note
string passed at each call site. With three sites (the ruling added one) that is three
copies of a literal that must not drift — the exact hazard `_render_pause`'s own
docstring is built around. I hoisted it to a module constant and made the parameter
default to it:

    PREFLIGHT_NOTE = "nothing has run yet; resume when the window resets"

    def _preflight_gate(ws, config, pace, state, *, note: str = PREFLIGHT_NOTE)

This is a strict superset of the brief's interface — `note=` is still accepted, so
anything in Task 7 wanting a different note is unaffected. The note text stays pinned by
the existing `test_pace_loop.py:743` assertion (`"nothing has run yet" in captured.out`).
Flagging it because it is my judgement call, not the brief's text; trivially revertible
to three literals if you would rather.

## How the run_resume gate turned out

Not awkward — it fits cleanly, no BLOCKED. `_preflight_gate`'s signature needed nothing:
`ws` and `pace` are both already in scope at that point in `run_resume` (`pace` from
`_pace(...)` at the top, `ws` from `_resolve_run`). Scoped exactly as instructed, inside
the `if not ws.criteria.exists()` / `if ws.request.exists()` branch only; the ordinary
resume path is untouched and still reaches `_execute`'s own gate with nothing spent.

On the "is the checkpoint wrong for an already-paused session" worry: it is not. The
session is re-marked `paused` with the CURRENT verdict's `resume_after`, scope and
reason, which is correct — the old pause instant has passed and the new one is the
window the operator must now wait for. `mark_paused` is a plain rewrite of `session.json`
with `outcome=None, failures=[]`, and this branch has neither, so nothing is lost. The
run stays on `run list`'s attention list either way, and `request.json` is untouched, so
it can be resumed again (my test asserts both).
