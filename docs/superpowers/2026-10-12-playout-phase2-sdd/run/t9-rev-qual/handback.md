### Findings

#### Important
1. **Plan-mandated: a resolvable condition that comes back within the cooldown, after its "resolved" notice was delivered, stays silent until the next repeat (up to about 6 h).** Location: `antenna/src/alerts.ts`, `planAlerts`. The absent-key pass sends "resolved" on the first absent minute. The present-key branch `!e || (!e.active && age(nowMs, e.cleared_at) >= COOLDOWN_MS)` then treats a return within 15 minutes as continuing, and the repeat clock still runs from the original `last_sent_at`. So the operator's last message says "resolved" while the condition is active. I confirmed this with a probe in a scratch copy: urgent `clock-failed` raised at minute 0, absent at minute 1, present every minute from 5 to 299. The only sends were `["alert@0","resolved@1"]`, so about 5 h of an active urgent condition went unannounced after a "resolved". Realistic triggers are the flapping ones: `clock-failed` (one transient R2 PUT failure is urgent, resolved the next minute, then any recurrence within 15 minutes is silent), `waf-api`, `lead-low`, `index-write`, `guard-write`. There is also a rare spend-adjacent case: `tripped-spend` resolves and re-trips within 15 minutes (a corrupt guard.json right after a raise clears the trip, or flush-time jitter around the 900 s evaluation spacing, since `cleared_at` is flush time, up to about 75 s after the guard ran). The block itself still happens, so spend is not at risk. On-air status and the operator's picture are.
   This is plan-mandated: brief test 1 pins "resolved" on the first absent minute, and brief test 3 pins a silent return for the resolvable `waf-api`. Together they guarantee this behaviour, and R13 states both rules. Fix options, each needing a ruling:
   - (a) Defer the "resolved" notice until the key has been absent for `COOLDOWN_MS`. The entry stays active with a clearing timestamp. This also stops resolved/alert flapping noise, but changes test 1's timing.
   - (b) Once a "resolved" notice has been delivered, a return is always a new `alert`, so the cooldown only suppresses returns whose clearing was not announced. This changes test 3.
   - I recommend (a): it is what "a flapping API does not page every minute" actually wants.

#### Minor
1. **A valid-JSON alerts.json with a `null` entry wedges cloud alerts permanently.** Location: `alerts.ts` `dispatchAlerts` and `planAlerts`, absent-key loop, `e.active`. `prev` is only checked to be an object. With `{"stale": null}` and that key not present, `planAlerts` throws `TypeError: Cannot read properties of null (reading 'active')` (confirmed by probe). It throws before the PUT, so the file is never rewritten: every minute logs `alert-dispatch-failed` and nothing reaches ntfy or email, including `tripped-spend`. The clock keeps running, so hugo's dead-clock monitor does not cover it. It only happens after a hand edit (or a top-level array containing null). Fix: drop entries that are not non-null objects when building `prev`, the same way a non-JSON file is treated as `{}`.
2. **The trailing `batch` default is `COMPLETE`, which fails open.** Location: `alerts.ts` `planAlerts` and `dispatchAlerts`. A future caller that forgets the batch gets resolution on a partial batch, which is the "resolved: Station blocked: spend" failure AlertBatch exists to prevent. `alertSink` makes the argument required, so production is safe today. Ruling A mandated this default so the brief's tests run unchanged. Consider making it required and passing `COMPLETE` explicitly in those tests at the next touch.
3. **A first write uses an unconditional PUT.** Location: `alerts.ts` `dispatchAlerts`, `read.kind === "absent" ? undefined : read.etag`. Two overlapping first writers both succeed and the last one wins. This still only duplicates and never loses (the loser's sends are re-planned next minute), so the rule holds. `createJson` (If-None-Match: *) would match the guard's idiom. The ignored `putJson` boolean is deliberate, per the comment.
4. **An alert that was never delivered can still get a "resolved" notice.** A failed alert or repeat leaves the entry active with `last_sent_at: null`. If the condition clears before a channel accepts it, the next complete batch sends "resolved" for an alert the operator never got. A retried alert also goes out with kind `repeat`, though its channel text is identical. Cosmetic.
5. **No timeout on the email binding call.** Location: `alerts.ts` `emailChannel`. ntfy has `AbortSignal.timeout(10 s)` and `binding.send` has none. Sends are sequential inside the clock's `finally`, so a hung binding holds the invocation open. Not a spend issue (alerts are not per-request billed), but it is inconsistent with ntfy.
6. **The ntfy `Title` header carries `STATION_NAME` raw.** All condition titles are ASCII (checked), but a non-Latin-1 `STATION_NAME` makes `fetch` throw on the header, so every ntfy send fails and retries every minute. Latin-1 characters reach ntfy as mojibake. Either document `STATION_NAME` as ASCII or move the title to RFC 2047 or ntfy's `?title=` query.
7. **One assertion in the redaction integration test is vacuous.** Location: `test/alerts.test.ts`, "a WafError carrying...". The `acct-5e1d` check can never fail, because the account ID is not in the Rulesets path or error text. The tokens (`an-tok`, `waf-tok`) are under the 8-character threshold, so the literal-value path is not exercised there. The `redact` unit test covers literal values, so coverage exists. The integration test just looks broader than it is.
8. **`budget-file-invalid` is `once` with a constant key.** Its key carries no period, so a second, different invalid raise within 35 days of the first clearing, or a stale invalid file left in place across periods, is never alerted. The failure direction is safe (the guard uses the stricter base budget). The key comes from Task 6 and R13 says "once", so this is for the whole-branch review, not this task.
