#### Minor
1. **A probe from an earlier session can feed the new session's StallWatch** (`antenna/public/player.js`, `probe()`). The only check after the `await` is `if (!playing) return;`. If the listener presses Stop then Play while a probe is in flight, `playing` is true again. The old probe's verdict then lands in a watch that `start()` reset. `reset()` also clears `probing`, so a second probe can run alongside the old one. Two in-flight "offair" answers could then reach 2 verdicts after only one probe in the new session. Both answers would have to be genuine 403/ENDLIST responses, so there is no false off-air. It does break the "one at a time" property, though. Fix: keep a session counter (`const gen = ++session` in `start()`, and `if (gen !== session) return` after the await), or a token that `StallWatch.reset` invalidates.
2. **`probe()` has no timeout** (`player.js`, `fetch(STREAM, { cache: "no-store" })`). On a black-holed connection the fetch can hang for the browser's default timeout, which is minutes. `probing` stays true all that time, so no further probes run. That is the right outcome during a blip, which must not go off-air anyway. Still, an `AbortSignal.timeout(~8000)` would keep the probe cadence the documented 10 s. Any abort maps to status 0, which is "unknown", so this is safe.
3. **A backwards jump in position stops progress from registering** (`nowplaying.js:93`). `lastPos` only updates on forward progress, so if `currentTime` ever jumps back, nothing counts as progress until playback passes the old high-water mark. A media re-attach or native live re-sync could cause such a jump. The listener would then see "Reconnecting…" while audio is actually playing, and probes would run. The probes return "unknown", so it never goes off-air. Treating any change larger than epsilon (`Math.abs(positionS - this.lastPos) > 0.05`) as progress would fix it.
4. **The edited `hlsErrorNotice` line is 124 characters** (`nowplaying.js:27`), the only line over 120 in either file. Splitting it into `const resp = data && data.response; const nd = data && data.networkDetails;` would make it shorter and clearer.
5. **A player that stalls permanently while the station is fine keeps probing every 10 s and shows "Reconnecting…" forever.** A permanent stall here means no fatal error and no recovery. The spend side is fine: probes are edge-cache hits. The UX side has no way out besides Stop/Play. This is not in this task's scope; noting it for phase 4 (the full player).
6. `player.js` has no tests of its own (DOM wiring: `watch.reset` in `start`, the `!playing` guard, "Reconnecting…"). That matches the brief and the phase-1 pattern. All logic that can be unit-tested sits in `nowplaying.js` and is tested there.
